# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Keep this file current.** When a change makes anything here, or in `.claude/rules/`, inaccurate, update it in the same change. That includes adding, removing or renaming a model, provider, job, endpoint, command, directory or convention. If you notice something here is already out of date, fix it or tell the user.

## Status

A self-hosted server for ESP32 e-paper panels.
- It fetches data from sources (weather, iCal calendars, RSS feeds, notes, checklists), lays it out on grid-based dashboards, and renders each dashboard to a 1-bit bitmap for the panels it is assigned to.
- A server-rendered admin UI manages all of this.
- It runs on a home LAN and has no authentication.

- **Domain** (`app/models`):
  - `Source` holds fetched data. Its type-specific settings and `fetch!` live in a provider in `app/models/providers` (`WeatherProvider`, `IcalProvider`, `RssProvider`, `NoteProvider`, `ChecklistProvider`). Providers are discovered from that directory through the `Providable` concern, so adding a provider means adding a file. Each declares its label, icon, description, form attributes and refresh interval with `provides`. A provider whose data changes when it's edited rather than on a schedule declares `polls: false`, and its source offers no refresh interval or Test button.
  - **Feeds.** `RssProvider` reads any feed through `Feed` (`app/services/feed.rb`): RSS 0.9x/1.0/2.0, Atom, JSON Feed and podcast RSS, or a page URL whose `<link rel="alternate">` names a feed. Feedjira picks the parser and supplies titles, links and dates; `Feed` reads images from the XML itself (media, enclosures, iTunes and item `<image>`, then `<img>` in the entry's HTML). An item whose link is itself an image uses that link as its picture. An episode without art takes the podcast's; a site's logo stays on the payload's top-level `image`. Each item also keeps its `summary`, `author` and `fields`: every element and attribute by its path (`dc:creator`, `enclosure@length`, `media:group/media:title`; JSON Feed keys likewise), repeated ones joined, capped in count and length. `Http.get` follows redirects. A summary that only repeats the headline (Google News) is dropped, and feed text is decoded as HTML so every named entity comes out. A news tile merges all its feeds through `NewsFeed` (newest first, undated items dated by their source's last fetch, duplicate links dropped, each entry tagged with its source's `source_name`), as `EventFeed` does for calendars.
  - **Headline templates.** A news tile's headlines layout is drawn from its `NewsTemplate` (`app/models/news_template.rb`) instead of parts: a picture (none, left, right or above, in a size) and three lines. Each line shows a named field (title, summary, author, source, date, age) or a custom format of tokens, where any other token is a path into the item's `fields`. A line whose tokens all come out empty isn't drawn. The tile keeps it in `settings["template"]` (`Component` lists `templates:` layouts); a new tile starts with `AppSetting#news_template`, edited on Settings. Both forms render `news_templates/_fields` (`news_template_controller.js`), and `NewsHelper#headline_line` fills a line on the panel.
  - **Newspaper.** The newspaper component is a whole front page in one tile, in one of several styles of paper (`NewspaperStyle`). How it lays out, fits headlines and sets its pixel fonts is in `.claude/rules/newspaper.md`, which loads when you work on its files.
  - `Dashboard` is a grid (columns × rows, plus a theme) of `DashboardItem`s. Each item is a component (clock, calendar, weather, news, newspaper, note, checklist, text) placed on the grid and fed by one or more sources. `Component` is the registry of each component's layouts, accepted source types, settings and parts.
  - A **part** is something a layout draws that can be shown or hidden, and sometimes resized: the weather icon, event times. Parts are declared per layout (`Component::Part`) and saved per layout in the item's `settings` under `parts` and `sizes`. Partials read them through `DashboardItem#shows?` and `#size_of`. A part's default draws the layout as it was before parts existed, so a new part that changes the render defaults to hidden. `DashboardItemsHelper#part_hint` can put a line under a part in the inspector saying why it won't draw yet.
  - A tile's **look** (`TileLook`, `app/models/tile_look.rb`) is the same set of choices for every component: border, header, padding, alignment, text size, white on black, and a text and a header font from `NewspaperFont`. It's saved in the item's `settings["look"]`, read through `DashboardItem#look`, and edited in the inspector's folded Look group (`dashboard_items/_look`). Each choice is blank by default, leaving it to the theme, so an untouched tile renders as before. `renders/_item` draws the choices as `look--*` classes on the card (rules in `render.css`). `renders/dashboard` writes one `<style>` with the fonts the tiles chose (`TileLook.css`), each set at the multiple of its grid nearest the text size. The fonts reach only text that inherits the card's `--body-font`/`--header-font`; partials that set their own type (weather, the calendar lists' `t-*` rows) keep it.
  - **Text and tokens.** The text tile's body is Markdown, drawn formatted (the default layout) or as plain text. Text tiles and notes fill `{{TOKEN}}`s when drawn (`PanelTokensHelper#with_panel_tokens`): the time and date through `PanelTimeHelper`, `DAYS_UNTIL:<date>`, `GREETING`, `SERVER_URL` and the rest of `PanelTokensHelper::TOKENS`. The inspector lists them (`dashboard_items/_tokens`), with what each would draw now. An unknown token is drawn as typed.
  - **Markdown editor.** Text tiles, a note's source form and its phone page share one editor (`application/_markdown_editor`, `markdown_editor_controller.js`, buttons in `MarkdownEditorHelper`). Like GitHub's, it's a textarea whose toolbar and shortcuts (Ctrl/⌘ B, I, K) type the Markdown. Its Font and Size menus wrap the selection in type markers, which Markdown has no syntax for: `{font:<NewspaperFont key>}…{/font}` and `{size:small|medium|large|huge}…{/size}`. `MarkdownHelper` turns them into spans (within one block; anything else is drawn as typed) and adds the fonts' faces (`NewspaperFont#markdown_css`). A size is 1–4× the font's pixel grid (`--md-grid`, `.md-size--*` in `render.css`), so it stays crisp. Images pasted, dropped or chosen are uploaded through Active Storage's direct uploads (`@rails/activestorage`, pinned from the gem) and go in as `![name](/rails/active_storage/blobs/redirect/<signed id>/<file>)`. `MarkdownHelper#markdown` inlines such an image as a gray PNG variant no larger than 800×800 (a frame has no request to fetch through), keeps `http(s)` images, and drops any other. `MarkdownImages` finds them in texts. Uploads aren't attached to anything: `PurgeUnusedImagesJob` removes those no note or text tile refers to after a day, variants included. A blob over `MarkdownImages::MAX_BYTES` (10 MB) can't be created (`config/initializers/active_storage.rb`), and the Disk service refuses a body larger than the size declared.
  - **Font picker.** Anywhere a font family is chosen (a tile's look, a Custom newspaper's `:font` settings, the Markdown editor's Font menu) uses `AdminFormBuilder#font_select` or `FontPickerHelper#font_select_tag`: a real `<select>` that `font_picker_controller.js` draws as a select-only combobox, each choice set in its own font. The admin's faces and preview classes are `font_previews.css`, generated from `NewspaperFont` by `bin/rails fonts:previews` (a test fails when it's stale).
  - `Device` is a panel: size, bit depth, image format, dithering, refresh schedule, whether it draws the navigation strip, and last-reported telemetry. `DeviceDashboard` assigns dashboards to devices, in `position` then assignment order: the order the special function and a dial step through (`Device#step_dashboard!`, wrapping at either end). `Frame` stores rendered bitmaps, each with the dashboard it was rendered from.
  - `AppSetting` is the app's single settings row, read through `AppSetting.current` (memoized in `Current`). It holds the time zone, the panels' 12/24-hour clock, the week start, the server address, the units new weather sources start with, the headline template new news tiles start with, and the check-in schedule new panels start with. The schedule fields and their validations are shared with `Device` through the `CheckInSchedule` concern.
  - **Time zones.** `ApplicationController` and `ApplicationJob` run everything inside `AppSetting#apply`, which sets `Time.zone` and `Date.beginning_of_week`. A panel with a blank `time_zone` follows the app's (`Device#local_time`). Time zones are stored as IANA names. Times drawn on a panel go through `PanelTimeHelper` and the `panel_*` formats in `config/locales/en.yml`; don't `strftime` them directly.
  - **URLs drawn on a panel.** A frame is often rendered in a job, with no request to take a host from, so a URL drawn on a panel uses the server address (`AppSetting#server_url`, as `url_options`). Until it's set, anything that needs it draws nothing.
  - **Notes.** `NoteProvider` holds Markdown. Saving it writes the payload at once, with no job, and asks the panels showing it for a new frame (`Source#request_refresh!`). `renders/items/_note` draws it through `MarkdownHelper#markdown` (commonmarker, sanitized down to what a panel can draw), styled by `.note` in `render.css`. The note tile's `qr_code` part draws a QR code of the note's phone page (`PhonePageHelper#phone_page_qr_code`, rqrcode).
  - **Checklists.** `ChecklistProvider` keeps its items in a JSON column, `[{ id, text, done_at }]` (at most `MAX_ITEMS`, each read and validated as a `ChecklistItem`). Saving writes the payload and asks for frames, as a note does. It can start over daily or weekly (`reset`), with nothing run to do it: an item keeps when it was checked, and counts as done only if that's since the day or week began at the time drawn (`ChecklistItem#done?`). A new source's form takes its first items one per line (`new_items`). Once it's saved, its edit page edits the items with the phone page's own list (`checklists/_editor`), in a card below the source form, since its forms can't nest in that one: `sources/_form` renders a provider's `sources/providers/_<type>_outside` partial there when one exists. Each change from that page sends `back: "source"` and returns to it (`ChecklistScoped`). The checklist tile (`renders/items/_checklist`, `ChecklistsHelper#checklist_rows`) lists them or flows them into columns, with done items struck through, moved to the bottom or hidden (`Component::CHECKLIST_DONE_ITEMS`), and parts for the boxes (sized), how many are done, and a QR code of its phone page.
- **Data refresh** (`config/recurring.yml`):
  - `FetchDueSourcesJob` runs every minute and queues a `FetchSourceJob` per due source. That job queues re-renders when a source's payload changes.
  - `RenderAllDevicesJob` re-renders every assigned panel every 30 minutes.
  - `PurgeUnusedImagesJob` clears out unused Markdown images daily.
- **Render pipeline:**
  - `FrameComposer` renders `renders/dashboard` inside `layouts/render.html.erb`, whose only stylesheet is `render.css` (inlined by `InlineAssets`).
  - It screenshots the page in headless Chrome (`lib/browser_pool.rb`, via Ferrum) and converts the PNG to the device's format with `Bitmap` and `Dither`.
  - `GET /render/dashboard` serves the same HTML, which the builder's preview iframe shows.
  - **Navigation strip.** A panel with `show_navigation` draws `renders/_navigation` along the foot of every dashboard (`Device#navigation`): the previous dashboard, the current one with a pip per dashboard (a count past eight), and the next. The grid gives up that space (`body:has(> .nav)` in `render.css`); the CDE theme draws it as a Front Panel with `.paper-workspace`'s buttons. Changing a panel's assignments, or a dashboard's settings, asks for new frames, since the strip names them.
  - `POST /render/preview` draws a dashboard with the builder's unsaved changes applied in memory: its Dashboard settings and the open tile (`DashboardItem#draft`, which swaps in for the saved tile). It saves nothing. Changes that couldn't be saved draw their errors instead (`renders/invalid`). `FrameComposer.html` and both actions hand the view its tiles as `@items`.
  - The dashboard list captures nothing. Each card shows the newest frame rendered from that dashboard (`Frame#dashboard`) from `GET /dashboards/:id/thumbnail.png` (`Dashboards::ThumbnailsController`), or a placeholder until there is one. It serves frames through the `LastFrame` concern it shares with `Devices::LastFramesController`.
  - **Admin styling must never reach the render.** Don't add `render.css` to the admin layout, or admin CSS or JS to the render layout. After admin UI work, check that the `/render/dashboard` HTML is unchanged.
- **Device API** (`app/controllers/api`). It is TRMNL's BYOS protocol (https://docs.trmnl.com/go/diy/byos), spoken by TRMNL's own panels and by the sketch in `esp32/esp32_dashboard/`. It is deliberately unauthenticated. A panel names itself by MAC in the `ID` header and sends its API key (`Device#token`) in `Access-Token`.
  - `GET /api/setup` gives a panel its API key and a `friendly_id`: its claim code, shown on its screen until it is assigned a dashboard. It is idempotent by MAC (`Device.enroll!`).
  - `GET /api/display` is a check-in. It records telemetry from the headers and composes a fresh frame when one is due, requested, or forced: a button wake (`Update-Source: button`), the special function, which also moves to the next dashboard, or a `Navigate` header. `Navigate` isn't TRMNL's: it's a signed number of dashboards to step (`-1` is back one), sent by the sketch's optional dial, a rotary encoder that wakes the chip by ext1 and counts clicks while it's awake. It always answers 200; the JSON `status` is what the firmware acts on (0 OK, 202 nothing to show yet, 500 set up again).
  - `GET /api/images/:id` serves the frame a check-in pointed at. `Frame#filename`, from the checksum, is the panel's cache key: an unchanged image isn't downloaded again.
  - `POST /api/log` writes the firmware's logs to the Rails log, tagged `TRMNL`.
  - TRMNL's firmware decodes a BMP only at 800×480 1-bit, so other sizes are sent PNG (`Device.image_format_for`). Most panels report only battery voltage; `Device.battery_percent_for` estimates the charge.
  - A stock TRMNL joins by setting its API Server to this app's address in its Wi-Fi portal.
- **Admin UI:** Dashboards, Sources and Devices.
  - A dashboard has no show page. The list's cards show it, and the drag-and-drop builder (`grid_controller.js`) is both its new and edit page.
  - The builder's tile inspector (`dashboard_items/_form`, `item_form_controller.js`) lists a Show group of parts for each layout, and shows only the selected layout's. Adding, saving, moving or deleting a tile asks the dashboard's panels for a new frame (`Dashboard#request_refresh!`).
  - The preview updates as you edit. `grid_controller.js` copies the inspector's and Dashboard card's fields (its `draft` targets) into a hidden form and posts it into the preview iframe (debounced), so the preview is a real page with its own headers. Changing the component waits for the rebuilt form. Selecting another tile previews again without the discarded changes. Both forms' permitted fields live on the models (`DashboardItem::FORM_ATTRIBUTES`, `Dashboard::FORM_ATTRIBUTES`).
  - Settings (`SettingsController`, a singular resource) is a single edit page for `AppSetting`. Saving a change to the time zone, clock, week start or server address asks every claimed panel for a new frame.
  - A device has no show page either. The list claims waiting panels and shows the rest as cards. A device's edit page is its home: status, dashboards (assign, switch, unassign) and settings. Telemetry isn't editable.
  - Cards and the device page show a panel's last frame from `GET /devices/:device_id/last_frame` (`Devices::LastFramesController`). Unlike `/api/display`, it only reads: no check-in, no compose.
  - A note's phone page is `GET /notes/:id/edit` (`NotesController`, by `NoteProvider` id; `/notes/:id` redirects there). It's what the note tile's QR code or an NFC tag opens. It uses the `phone` layout: no sidebar or header, sharing `layouts/_head` with the admin layout. Both a note's and a checklist's source form show the link (`sources/_phone_link`, `PhonePageHelper#phone_page_url`).
  - A checklist's phone page is `GET /checklists/:id/edit` (`ChecklistsController`, by `ChecklistProvider` id), in the same layout. Every change is a form of its own with no JavaScript needed: toggling (`PATCH /checklists/:id/items/:item_id`, which sets done rather than flipping it, so a repeat is harmless), moving up or down (`…/move`), removing and adding (`Checklists::ItemsController`), and clearing the done ones (`Checklists::DoneItemsController`). Each redirects back, and Turbo morphs the page in place; `checklist_focus_controller.js` puts keyboard focus back, since Turbo disables a button while its form is sent.
  - It is built on the vendored CoreUI 5.9 Bootstrap admin template (`vendor/assets`, `vendor/javascript`), with `AdminFormBuilder` as the default form builder.
  - Section index pages open with the `page_header` helper's banner (`application/_page_header.html.erb`); inner pages with `page_title` (breadcrumb and heading).
  - Every area is restyled. Only the scaffold `dashboard_items` index, show and new pages are left as generated.
- **Tests:** Minitest tests for models, services, controllers, helpers, the form builder and admin-layout integration. Of the jobs only `PurgeUnusedImagesJob` has tests, and the mailers have none. There are no system tests either: `test/system` doesn't exist, though CI still runs `test:system`.
- `public/ditherer.html` is a standalone dithering tool, separate from the Rails app.

## Commands

- `bin/setup` — install dependencies, prepare the database, start the app (`bin/setup --skip-server` to skip the server).
- `bin/rails test:system` — Capybara + Selenium system tests (none exist yet; not run in `bin/ci` by default).
- `bin/ci` — full local CI pipeline (see `config/ci.rb`): setup, RuboCop, bundler-audit, importmap audit, Brakeman, tests, seed replant.

## Conventions

- **Accessibility: WCAG 2.2 AA.** Every admin page must meet WCAG 2.2 AA in both the light and dark themes:
  - text contrast ≥ 4.5:1; focus indicators and control boundaries ≥ 3:1
  - everything keyboard-operable, with a single-click alternative to any drag
  - labeled controls, landmarks, status messages in live regions
  - reflow at 320px without the page scrolling sideways

  Reuse the tokens and components in `app/assets/stylesheets/application.css` (`--app-focus-ring`, `--app-control-border`, the `--app-*-on-light`/`-on-dark` colors, `.btn-app-outline`) instead of CoreUI defaults, several of which fail contrast. Verify in a real browser (e.g. axe-core in headless Chrome via Ferrum), not only by reading CSS. The e-ink render (`layouts/render.html.erb`, `render.css`) is a 1-bit panel image and is out of scope.
- **DRY.** Before adding something, look for an existing helper, partial, `AdminFormBuilder` method, Stimulus controller or CSS token, and reuse it. When something repeats, extract it: markup into partials or helpers, form styling into `AdminFormBuilder`, colors into CSS custom properties, user-facing strings into `config/locales`. Keep duplication only for a concrete reason, stated in a comment (e.g. the inline color-mode script that must run before first paint).
- **Rails 8 conventions.**
  - Use current framework idioms: `params.expect`, the Rails 8 helper names (`textarea`, `checkbox`), `tag`/`class_names` over string-building, I18n for copy.
  - In Stimulus, use targets, values and params, plus action filters and options (`keydown.enter->grid#pick:prevent`), rather than hand-written event handling.
  - Stay on importmap and Propshaft, with no Node build.
  - Keep pages CSP-ready: no inline event handlers or `style` attributes, and `javascript_tag nonce: true` for any inline script that can't be avoided.
  - Tests mirror `app/` (`app/form_builders` → `test/form_builders`); layout-wide behavior goes in `test/integration`.
- **American English** in comments, UI text, commit messages and docs: color, behavior, gray, center, initialize, labeled, enroll.

## Architecture

- **No Node build step.** JavaScript is managed by `importmap-rails` (`config/importmap.rb`); Stimulus controllers live in `app/javascript/controllers/`. Assets are served by Propshaft.
- **SQLite for everything, across four databases in production** (`config/database.yml`): `primary`, plus dedicated `cache`, `queue`, and `cable` databases with separate migration paths (`db/cache_migrate`, `db/queue_migrate`, `db/cable_migrate`). Development/test use a single SQLite file each in `storage/`.
- **Solid adapters** back the framework: `solid_cache` (Rails.cache), `solid_queue` (Active Job), `solid_cable` (Action Cable). Jobs run inside the Puma process in production (`SOLID_QUEUE_IN_PUMA=true`); recurring jobs are defined in `config/recurring.yml`. In development `bin/dev` starts no worker, so queued jobs sit unrun unless `SOLID_QUEUE_IN_PUMA` is set: anything a page or the preview needs right after a save can't wait on a job.
- **Headless Chrome** is a runtime dependency of the render pipeline (Ferrum). The Docker image installs Chromium and points `CHROME_PATH` at it, with `config/fontconfig/local.conf` as `/etc/fonts/local.conf` to turn off text antialiasing: Linux Chromium ignores `-webkit-font-smoothing`, and antialiased text at fractional x comes out distorted in 1-bit. Locally Ferrum finds an installed Chrome (macOS honors the CSS, so it never showed there).
- **Deployment** is via Kamal (`config/deploy.yml`, `bin/kamal`) as a Docker container (`Dockerfile`), with `storage/` on a persistent volume so the SQLite databases and Active Storage files survive deploys. `thruster` fronts Puma for asset caching/compression.
- **Active Storage** is configured with `image_processing` (libvips) for variants. It holds the Markdown editor's image uploads.
